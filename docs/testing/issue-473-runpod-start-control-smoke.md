# RunPod retained compute Start — temporary Linux smoke plan

## Candidate and proof boundary

Bind a clean reviewed candidate commit/tree and all source hashes before any build.
Record GUI/fixture binary hashes, build logs, lockfile parity and runner hashes.
Do not reuse a consumed runtime directory or relabel an older screenshot as this head.
This is a synthetic local UI/control proof, not actual RunPod billing, allocation,
retention, filesystem durability, backup or successful cloud Start acceptance.
Configured/core tests prove the real durable coordinator using injected providers.
The stock GUI must never receive a live API credential or reach the provider network.

## Preconditions and isolation

1. Wait for independent source review and the shared-cache build window. Build the
   exact candidate with debug GUI and an external public-API fixture helper.
2. Allocate a new private proof directory and explicit private fixture root. Record
   baseline Horizon/Pi PIDs and owned display/server identities without touching them.
3. Select an unused Xvfb display, launch one task-owned window manager, and isolate
   HOME/config/session directories. Unset HORIZON and provider credentials for children.
   Use `--config <private-config> --ephemeral` and a disposable non-login shell.
4. Deny AF_INET/AF_INET6 provider connections for the candidate/fixture; permit only
   its owned X11 Unix socket. Record child commands and connection attempts. Never
   focus an existing Horizon window or run browser automation.
5. Seed only synthetic workspace rows through store create/allocate/reserve/recover
   and explicit Stop/Start coordinator APIs with a fake provider. No SQL mutation
   for ordinary fixture setup. Use valid generated synthetic public SSH keys, exact
   saved HPS intent and inert RunPod profile. No private-key material is necessary.

## Fixture inventory

- RunPod persistent saved Stopped, exact worker, saved public pin and HPS selection.
- RunPod persistent saved Starting with its original request timestamp.
- RunPod Ready, Stop pending and both deletion phases: Start is unavailable.
- Ordinary Azure Stopped record/profile: its existing Start eligibility and declared
  cost disclosure remain intact. Local Docker is not newly offered Start.
- Separate absent/legacy storage fixture: Start cannot create or migrate storage.

Snapshot saved allocation/workspace/HPS rows and protected fixture bytes before launch.
Retain those snapshots for post-close comparison. Do not populate real user repositories.

## Native interaction and visual coverage

1. Launch at 1200×900. Identify the actual mapped window by exact candidate PID.
   Capture and inspect a settled launch screenshot; open the overview normally.
2. Select RunPod Stopped. Assert Start enabled, Stop disabled and saved Stop check
   unchanged. Open Start by pointer click. Capture and inspect the full confirmation.
3. Confirm exact workspace, owner, profile and resource ID; billing resumes without
   an invented hourly quote/cap; HPS remains separately billable; no task/process
   memory resumes; no private SSH key; five-minute provider observation bound;
   close is not cancellation; uncertainty may already be billable. No Azure CLI text.
4. Press Enter without activating the button, then Cancel. Neither grants Start.
   Reopen confirmation, change selection/config, and ensure stale consent cannot send.
5. With a deliberately absent RUNPOD_API_KEY, explicitly click Confirm once. The
   actual callback reaches configured admission/credential refusal without provider
   traffic or a saved Start intent. Display a truthful Start-specific failure, not
   a Stop failure. Do not inject a fake provider response into the stock GUI.
6. Select the saved Starting row. Start is offered as an explicit retry; no automatic
   replay occurs from selection, refresh, overview reopen, pointer movement or idle.
   Pending and successful typed-result rendering are additionally covered by the
   deterministic UI tests; do not label those tests as a live provider operation.
7. Check Ready/Stopping/DeleteRequested/Deleted/LocalDocker refusal controls. Check
   the Azure positive control still displays its existing identity and price text.
8. Resize to the actual minimum 800×600. Repeat Stopped confirmation, scroll as needed
   to reach both buttons, verify no clipped identity/warnings, and capture screenshots.
9. Restore 1200×900. Close/reopen overview and Refresh. No callback repeats. Exercise
   available Fit only if the fixture has meaningful board content; report N/A otherwise.
10. Compare idle and scripted pointer movement over empty overview space and controls:
    no new background provider request, no unconditional busy repaint loop, no changed
    persisted state. Retain observations separately from still screenshots.

## Failure and state tests required before native

Real-store fake-provider tests: missing HPS/pin/profile, stale selection, nonpersistent
or wrong identity, conflicting intent, credential failure, mutation while credentials
resolve, HPS/workflow drift during provider call, one dispatch, absent/foreign endpoint,
retained uncertainty and explicit existing-running retry. Completion requires exactly
the original worker and the permitted revision/Reconciling result.

UI tests: no implicit Enter/cancel action, consumed consent/config drift, wrong callback
kind, incorrect revision/identity/result, single flight, late result discarded after
close/selection/config change, and absent/incompatible store noncreation. Existing
Azure tests must pass unchanged with the backward-compatible result alias.

## Normal close, evidence and disposal

Send one normal WM_DELETE_WINDOW to the exact candidate window. Verify exit 0, task
display/WM termination and unchanged preexisting PIDs. Preserve any timeout/failure;
do not automatically rerun or conceal forced cleanup as normal close.
Recheck saved/protected snapshots, child commands and network denial logs. Record
every screenshot path/hash and actual inspection, completed/N/A lanes and limitations.
Archive this plan privately after the pass and remove only this temporary repository
plan using apply_patch before the final exact-head full validation matrix.
