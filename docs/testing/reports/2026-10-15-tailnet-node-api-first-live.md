# Exact-node SDK first live check

## Scope and inputs

On 2026-10-15, two sequential Hetzner cpx22/fsn1 CPU workers qualified the desktop
`NodeApi::delete_recorded` transport with a Personal API token and OAuth.
The checked SDK source snapshot was tree
`ec4f10a58f745f3d1abfaac798d76d0a5b65a502`; both lanes used the same frozen
private adapter, SHA256
`ac3de30b370ef52c61435df44565811f14054343db6292f90b9ea49a176cacf1`.
The workers used the immutable marker-4 base image ending
`f28a0ceb76b559b299000b440a26951bc70a820003d3911c4e130174bef944ec`.

This report records first live SDK evidence under the
[exact-node procedure](../procedures/tailnet-node-api.md).
It does not qualify a final reviewed SDK head. The SDK remains unwired to cloud
deletion and public UI, CLI or MCP mutations. Core automatic cleanup, card removal
and retry behavior are outside this outcome.

## Exact authority and provider absence

Both workers reached Ready. The desktop recorded each actual Self device ID with
its original saved-tailnet, allocation, provider and worker binding. Deleting the
provider resources retained that exact enrollment receipt.

Separate observations then confirmed the original server, volume and provider
SSH key returned 404 and their exact operation collections were empty.
Only after this proof did the trusted desktop adapter permit the SDK call for
that recorded device ID. Two original device/API-ID pairs were protected exclusions.
No name lookup, first-peer inference, numeric-ID substitution or broad deletion
provided authority.

The private desktop test adapter validated the trusted operator’s attestation
before invoking the SDK. The SDK did not independently inspect providers or
update the product enrollment ledger. The host and its credential store remain trusted.

## Personal token

The token was bound to the task's captured saved-tailnet ID on the desktop.
Actual SDK deletion returned `confirmed_deleted`. Repeating the call returned
`retained` with `not_found_unverified`. A 404 did not become deletion confirmation.

The exact task API binding subsequently reported missing while the saved catalog
and enrollment binding remained available for final cleanup.

## OAuth refusal and successful deletion

A first task OAuth client used `devices:core` and the worker tag. After its
revocation, actual SDK exchange returned `retained` with `authorization`.
A subsequent read-only observation still contained the same exact recorded node.
The refusal therefore left a real node present before positive deletion.

The first client's local binding was cleaned up. A distinct second client was
then bound to the same task saved-tailnet ID. Actual SDK deletion returned
`confirmed_deleted`; repeating returned `retained/not_found_unverified`.
Both task clients recorded confirmed revocation and missing local bindings.
Tag selection was not treated as proof of restricted device-removal authority.

## Reconciliation and limits

Before/after receipts contain the same two original protected node/API-ID pairs.
Final operator inventories contain exactly those two devices and neither task
node. The task auth keys were revoked. API bindings reported missing before final
Auth/catalog cleanup, and the original task journals recorded that cleanup.
The Personal lane finished cleanup before the OAuth worker was created.

Typed SDK outputs explicitly record `product_ledger_updated: false` and
`independent_provider_verification: false`. This was SDK transport qualification,
with separate provider proof and trusted desktop authority. It did not activate
Core cleanup, introduce public MCP deletion, expose an API credential to a worker
or establish a boundary against arbitrary same-user desktop code.

The private evidence retains the typed outcomes, exact capture/provider bindings,
protected-pair comparisons, artifact provenance and cleanup records. This public
report omits private resource IDs, account details, credential slots and paths.
Final-head real-input validation remains required before release readiness.
