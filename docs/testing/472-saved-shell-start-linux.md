# Explicit saved Shell start: temporary Linux smoke plan

Use an isolated task-owned Horizon home and exact candidate binary/display/PID.
Never alter a pre-existing Horizon process, desktop, cloud worker or repository.
Record source/binary and fixture provenance; do not expose credentials or user
commands in public evidence. Use synthetic saved commands and data for screenshots.

## Preconditions

- Seed an existing owned persistent worker with retained SSH identity/full pin and
  a completed Git preparation for a synthetic repository, explicit branch and
  nested working directory. Use the installed worker APIs; record fixture setup
  separately from task-start UI proof.
- Include two independent Shell intents and an already-exited task. Record task
  identities/start counts, dirty nested bytes and an independent progress counter.
- The candidate's active persistent session must actually own the saved workspace.
  No local checkout is required and no new provider allocation is implicit.

## Main flow and confirmation

1. Capture launch. Open Environments and Show saved panels. Inspection and Reopen
   retain their existing meaning; opening the overview starts no remote task.
2. Request Start for one saved Shell. Verify read-only preparation and the exact
   repository, branch, directory and literal argv. Cancel; verify zero starts.
3. Prepare again and explicitly confirm. Verify one remote task with its saved
   nested directory, a clear result, and no automatically attached client view.
4. Inspect it. Repeating an explicitly confirmed start must not replay the task;
   an already-exited matching task must remain exited. Verify original identities,
   single-start counts and dirty data.
5. Close the view/overview and candidate normally. Independently verify ongoing
   worker/task progress. Reopen using the same isolated saved state and inspect;
   do not confuse view restoration with task execution or provider creation.

## Errors, drift and interaction

- Wrong owner, missing pin/key, mismatched profile, incomplete Git setup and expired
  runtime reject without starting. Use deterministic tests for variants not
  separately native-executed and label coverage honestly.
- Change the saved command/allocation/selection between preparation and confirm;
  execution must refuse the changed snapshot, not run a newly substituted command.
- Lost/invalid reply or post-start drift is unknown, never automatic retry. The
  user can inspect; confirmation and stale prior status must not imply success.
- Switch selection/session/config or close the overview during work. Discard stale
  presentation results while retaining one in-flight operation; never claim this
  revokes remote bytes already sent or stops an independent task.
- Resize/Fit, scroll a long command, check keyboard focus and cancellation. Capture
  screenshots and native geometry/motion as applicable; verify no overlap or
  accidental confirmation. Test light mode or deterministic theme adaptation.
- Compare idle and pointer-only behavior: no background polling, no repeated task
  start/preparation and no new per-frame provider/filesystem work.

Cleanup only exact task-owned fixtures after independently reviewing the evidence.
Keep the final test result's claims separate from real RunPod image pull/storage,
GitHub operations and client-off acceptance. Remove this temporary plan after the
required native pass and preserve private evidence outside the repository.
