# Retained RunPod first-Stop controls — temporary Linux smoke plan

## Scope and authority

Validate the final candidate's explicit first-Stop route, confirmation and fixed
missing-credential refusal on a fresh synthetic public-only store. No real RunPod
key, private SSH key, cloud request, container, provider Stop, task submission,
token, registry or user's desktop is part of this lane. This is not a positive
cloud retention or billing proof; the genuine H200 campaign is historical only.

Root reviews the source, fresh helper adaptation and exact binary bindings before
any build or runtime. Do not reuse consumed fixture roots, intent files, displays
or old screenshots. The same isolated native pattern used for saved-Stop checking
is reusable code, not evidence for this candidate. Archive this plan privately
and remove it from the product tree only after the completed validation review.

## Preparation and preconditions

1. Record final candidate head/tree, clean source state, lock hash, helper manifest
   and immutable debug GUI/fixture-driver hashes. Compile with the reviewed cache
   lock and copy the exact outputs privately. Run bounded pure helper tests and
   dependency parity first. No release build is needed.
2. Create a new private task root (0700), files0600 and child-only environment.
   Every invocation uses `umask 077`. Unset HORIZON and all provider credentials
   in the child; do not read, rename or alter any real user's keys/configuration.
   Preserve each failed artifact/intent rather than replaying a consumed action.
3. Seed only synthetic public retained metadata through public store APIs: one
   persistent RunPod Ready worker with exact saved workflow/job/resource ID,
   digest-pinned target, named profile, HPS selection and complete public SSH pin;
   no Stop intent, no private identity, no cleanup and no pending setup operation.
   Include one dormant row and one public Stopping row for eligibility/handoff
   checks. The Stopping row is fixture metadata, not a provider operation.
4. Snapshot all cloud-store domain rows, schema/version/journal, selected HPS,
   config and absent private identity. This snapshot must remain unchanged;
   ordinary blank local session bookkeeping is separate, not immutable-home proof.
5. Launch only on an explicitly verified-unused task-owned X11 display with a
   task-owned window manager, fresh private home, `--blank`, explicit disposable
   shell and no restore. Bound the entire campaign to15minutes. Trace only the
   owned candidate child tree; fail on SSH/provider subprocess or setup dispatch.
   Capture exact PID/window identity before any coordinate operation. Do not
   inspect or signal any pre-existing process, container or display.

## Baseline and primary flow

1. Capture1200x900 baseline. Empty canvas and disabled/inert empty-board Fit are
   the expected baseline; do not claim functional populated-board fitting.
2. Open Environments once and select the synthetic Ready RunPod row. Confirm
   saved state is labeled saved, Stop environment is enabled and Check saved Stop
   is disabled. No provider observation or creation may occur on selection/open.
3. Open Stop confirmation. Read exact workspace/owner/profile/resource identity,
   all-process stop/process-memory-loss warning, exact saved HPS/public-pin
   requirement, no-private-key disclosure, no filesystem durability/backup claim,
   no volume deletion and possible continuing storage cost. Ensure no local
   container-retention promise appears for RunPod.
4. Capture the confirmation screenshot. Press Escape/cancel and verify no Stop
   thread, provider/key activity, local intent or store change. Reopen confirmation;
   Enter without deliberate button activation must not submit. Cancel again.
5. Confirm exactly once through the visible button. Expect one explicit Stop
   worker, then saved inventory refresh, and fixed RUNPOD_API_KEY refusal. No
   durable Stop intent is created because credentials were refused first. Verify
   the source-level trace/counter invariant, exact unchanged store and key absence.
   This refusal is not evidence that a provider request was dispatched.
6. After completion settles, reselect the same row and verify readable failure
   notice and retry guidance: refresh and use Check if intent exists, never resend
   an already-admitted Stop. Closing the overview is not cancellation; exiting
   Horizon can interrupt local coordination. Record visible wording honestly.

## Negative, persistence and interaction lanes

- Select the Stopping fixture row: first Stop must be disabled and Check enabled.
  Do not execute Check in this lane unless separately included in the reviewed
  action/count manifest. Existing core tests prove the observer-only handoff and
  original timestamps, not this screenshot.
- Select dormant/timed/unsupported fixtures when seeded: no first-Stop admission.
  Do not create new fixtures ad hoc during runtime; bind them in advance.
- Manual refresh, select-away/back, overview close/reopen, three seconds idle and
  pointer movement over empty modal space must not dispatch Stop/setup/provider
  work. Wait for each preceding asynchronous operation to settle before asserting
  stable counters. In-flight single-flight/late-result behavior uses deterministic
  unit callbacks; a quick missing-key refusal cannot prove an observed live wait.
- Resize to960x720 with24bounded native geometry samples, scroll only the owned
  modal as needed and capture readable Stop/Check/confirmation/warning/result
  controls. Restore1200x900 with24samples and capture stability. Use screenshots
  plus geometry traces; do not infer motion stability from one image.
- Close overview and click the disabled empty-board Fit control once; record it
  as inert empty-board behavior. No terminal/workspace creation is permitted.
- Missing, insecure, actual legacy v6 and current-schema/index/trigger drift are
  covered at the actual callback boundary by local-store tests. Bytes, version,
  permissions and journal remain unchanged; valid-current configuration refusal
  is the positive non-storage control. No cloud/key calls are needed for these.
- Core tests cover exact request/profile/HPS/pin admission before lazy key access,
  full workflow and selection drift at both boundaries, full-allocation intent CAS,
  one fake Stop, failure/absence intent retention, replay refusal and redaction.
  They are synthetic evidence, not ownership attestation or retained-byte proof.
